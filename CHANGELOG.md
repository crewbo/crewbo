# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- A task run that changed nothing said "no checkpoint: git user.name and user.email are not set" when git had no identity. An identity is now asked for only when there is something to commit.
- A task kept showing a conflict (in `crewbo task list`, the dashboard and the editor extension) after it was merged or cancelled, or after the other task was. Those conflicts are no longer listed.
- `crewbo doctor` failed when an installed agent had no Crewbo hooks, even if the member uses another agent with Crewbo. That is now a warning; it still fails when no agent has hooks.
- The VS Code extension listed every task the daemon knew, from all rooms, by id. It now lists only the tasks of the rooms of the open folders, labelled by their text (`task_list` takes an optional repository).
- `crewbo task approve` treated any character device as a terminal, so a command run by an agent (stdin on `/dev/null`) reached the "Type yes to approve" prompt instead of being refused at once. It now requires a real terminal; nothing was approved, because nothing could type `yes`.
- `crewbo login` gave up the whole sign-in when one check with GitHub got no answer (seen twice on a slow network during the M4 two-machine check). A lost check is now retried at the next interval until the code expires, and an expiry says what the last network error was.
- An agent working in a git worktree (`git worktree add`) was not blocked by claims made in the main checkout or shared by teammates, because Crewbo treated each worktree as a separate repository. A linked worktree now shares its repository's claims and room.
- When the hook could not get an answer from the daemon for any reason, it always said the daemon "did not answer in time". It now says that only for real timeouts and names the actual failure otherwise.
- The daemon took minutes to notice a silently lost network (for example Wi-Fi turned off) and kept showing "connected". It now pings the sync server and shows "offline, retrying" within about 30 seconds.
- A claim a teammate made from their terminal was described as their agent's ("gavriel953's agent") in hook messages, `crewbo claim list` and the MCP tools once shared through a room. It now says "(from a terminal)" again.
- `crewbo hooks install` could hang forever when `claude --version` stalled and left a child process holding its output (for example a version-manager shim without network access). It now gives up after the 5 s timeout plus 1 s.
- `crewbo claim add` treated flags placed after the paths (`claim add src/a.go --task 12`) as extra claims.
- `crewbo hooks uninstall` replaced the `.crewbo.bak` backup with the hooked config, so the original was lost. The backup is now written only from a config without Crewbo hooks.
- `crewbo hooks install` and `uninstall` re-sorted the keys of `settings.json` and wrote `&`, `<` and `>` as `\u0026`, `\u003c` and `\u003e`. Key order and characters are now kept, and an install and uninstall give back the same file.
- `crewbo hooks uninstall` left a Codex `hooks.json` containing only `{}` (or created one when nothing was installed). A config left empty is now removed.

### Added

- Sign in, create a room or join one from the editor: the crew panel of a repository outside a room offers **Sign in with GitHub**, then **Create a room** and **Join with a code**, which run `crewbo login`, `crewbo room create` and `crewbo room join` in a terminal. The same commands are in the Command Palette under Crewbo.
- A lead can ask their own agent to split the work: the new MCP tools `crewbo_crew` (who is in the room and what they are doing) and `crewbo_draft_task` let the agent draft one task per teammate. Drafts are never sent by the agent: the lead reviews, edits and sends or drops each one under **Drafted tasks** in the Crewbo view.
- The Crewbo IDE (preview) opens the crew panel on first run, and offers to install Claude Code and Codex from Open VSX if they are missing.
- The room lead can send a task from VS Code: **Send a task** at the top of the Crewbo view asks who, which files and what to do, then signs and sends it like `crewbo task create`.
- In VS Code, a claim in the Crewbo view shows the holder's Bo in their teammate colour, and a file a teammate holds shows who has it and with which agent (`riya · Codex`) at the end of its first line.
- The VS Code extension has a crew panel (the Crewbo icon in the activity bar): one row per member with Bo in their teammate colour, writing, idle, asleep when offline, or with a face for a conflict or a pending handoff, plus what they are doing and which agent they run.
- `crewbo crew` shows the room of the current repository: each member, whether they are online (or since when they are not), what their agents are doing (`Writing src/auth.go`, `Idle`) and the files they hold. Daemons now share each agent's name and the file it is about to edit with the room, live and not stored (see the privacy page).
- `crewbo task list`, `crewbo task show`, the dashboard and the editor extension list teammates' tasks too: tasks they started for themselves, with the start of their text (up to 4 KiB), and tasks the lead sent to someone else, with their latest state.
- The VS Code extension can be installed from a `.vsix` file: `task ext:package` builds it, and each release will attach it.
- `crewbo report` prints counts of your Crewbo use to paste into the dogfood survey: Crewbo version and OS, which agents ran on this computer (sessions, first and last day), each room's members, merged tasks, conflict warnings, handoff requests and lead overrides, active claims and your tasks by state. It holds no file paths, task text or names, and sends nothing.
- `crewbo doctor` checks this computer's Crewbo setup and prints a fix under each problem: the daemon, your sign-in and whether the sync server answers, the room for the current repository, your git name and email, the binary's folder, each agent's hooks and whether they have fired since the daemon started, and whether your login shell prints anything that would break hook replies. It exits with an error when something must be fixed.
- Antigravity support: `crewbo hooks install --agent antigravity` (also part of `--agent all` when `agy` is installed) adds a named `crewbo` hook set to `~/.gemini/config/hooks.json` and Crewbo's MCP server to `~/.gemini/config/mcp_config.json`. An Antigravity agent is then denied edits and shell writes to files a teammate has claimed, with the same message as Claude Code and Codex, and sees a note before its model calls when Crewbo has something to say. Tested with `agy` 1.4.2 on Linux.
- `crewbo device list` shows the device keys registered to your account, and `crewbo device revoke KEY-ID` retires the key of a lost or replaced computer: teammates reject tasks signed with it, and you are signed out everywhere. See `docs/runbooks/device-key-rotation.md`.
- `crewbo task cancel ID [--reason TEXT]` stops a running or checkpointed task, yours or one you sent as the lead: the agent stops, the task's claims are released, and the room sees it cancelled. Its worktree and branch are kept.
- `crewbo dashboard` prints the address of a read-only dashboard the daemon serves on this computer: claims, tasks with their conflicts, and handoff requests, refreshed every 2 seconds. The address holds a token and works until the daemon stops.
- Crewbo for VS Code, v0 (run from source with `task ext:run`): a Crewbo view in the Explorer lists the room's claims with their task, your tasks and their conflict warnings, and handoff requests; claimed files show the holder's initials; the status bar counts claims, open handoff requests and conflicts. You can ask for a file, answer with Hand off or Not yet, release a claim as the room lead, and review a task, which you then approve in a terminal with `crewbo task approve`.
- `crewbo api` passes requests to the local daemon over stdin and stdout as JSON lines, for editor extensions. It cannot approve tasks; use `crewbo task approve` in a terminal.
- The escalation ladder for claims in a room: `crewbo claim request PATH [--reason TEXT]` asks the teammate holding a claim on PATH to hand it over; they answer with `crewbo claim handoff REQUEST approve|decline [--reason TEXT]`, and an approval releases the claim so you can take it. The room lead can release any claim with `crewbo claim override PATH --reason TEXT`. `crewbo claim requests` lists the room's requests, answers and overrides. When a hook blocks an edit, its message now names the `crewbo claim request` command.
- `crewbo login --server URL` recognises a new address of the server you are signed in to (for example a restarted tunnel) by the server's public id, and moves your sign-in and rooms there without signing in again. After a normal sign-in, rooms the server already has move to it too. `GET /v1/info` gives the id; sessions saved before this change need one more sign-in to record it.
- `crewbo task start --branch NAME` makes an existing branch a task, so work begun before Crewbo gets claims, checkpoints, conflict checks and merging too. The task is worked on where the branch is checked out, your own checkout included, or in a new worktree; the main branch itself cannot be registered.
- Tasks you start yourself are checkpointed when your agent finishes a reply, at most every 5 minutes, or at once with `crewbo task checkpoint ID`; they get the same conflict checks as dispatched tasks and merge with `crewbo task merge`, which then releases their claims. A conflict that a later checkpoint resolves disappears from everyone's task list.
- `crewbo task start [--path PATH]... TEXT` gives you a task of your own, with no lead or approval: a new git worktree on branch `crewbo/<task id>` at your current commit, with the paths claimed for whatever agent you open there (for up to 8 hours). The room sees it running. Checkpoints and merging for these tasks follow.
- `crewbo room set --merge lead-only|members` (lead only) chooses who may run `crewbo task merge` in a room: each member for their own tasks (the default), or only the lead. `crewbo room status` shows it. It is a Crewbo rule, not a lock: plain `git push` still works unless the repository protects its main branch.
- A lead can also run `crewbo task merge ID` on a task they sent, once its assignee's work is checkpointed: the lead's machine fetches the checkpoint and merges it as the lead, and everyone, the assignee included, sees it merged.
- `crewbo task merge ID` puts your checkpointed task into the remote's main branch as a merge commit, without touching your working copy. It is refused when the task conflicts with main, or with another task's checkpoint; after talking to that task's owner, `--despite OTHER-ID` merges anyway. If someone else pushed to main meanwhile, Crewbo checks again and retries.
- Conflict warnings across machines: after a task's work is checkpointed, Crewbo fetches the latest checkpoint of every other task in the room and checks them with `git merge-tree`. Conflicting pairs are announced to the whole room; `crewbo task list` flags the affected tasks and `crewbo task show` names the other task and the files, so they can be sorted out before anyone merges.
- When a task's agent finishes cleanly, Crewbo commits its work on the task branch as you (your git `user.name` and `user.email`) and pushes it to `refs/crewbo/<you>/<task id>` on the repository's remote, or to the branch `wip/<you>/<task id>` if the remote refuses that ref. The task is then checkpointed and the lead sees where. If nothing changed it stays finished; if the commit or push fails, it says why and the work stays in the worktree.
- `crewbo task list` on the lead's machine also shows the tasks the lead sent, with the state their assignee last reported (approved, declined with the reason, expired, running, finished or failed); `crewbo task show` marks them "sent by you". A task that ends cleanly is reported as finished.
- `crewbo task approve ID --agent codex` runs the task with Codex (`codex exec --sandbox workspace-write`) instead of Claude Code, on Linux and macOS; Windows is refused until Codex's sandbox works there. Crewbo checks `codex login status` first and reports why a run failed. Any agent working in a task's worktree holds the task's claims.
- `crewbo task approve` now runs the task: Claude Code works on it in a new git worktree (under Crewbo's data directory, on branch `crewbo/<task id>`, starting at the lead's commit), with the task's paths claimed for it and kept claimed while it runs. Before approving, Crewbo checks that your clone has the lead's commit and that Claude Code is signed in, so you can fix either and approve again. `ANTHROPIC_API_KEY` is removed from Claude Code's environment unless you pass `--use-api-key`. The worktree and a log are kept after the run; the lead is told when it starts and if it fails.
- `crewbo task list`, `show ID`, `approve ID` and `decline ID [--reason TEXT]` for tasks sent to you. `show` prints the whole task, with any control characters (such as terminal escape codes) shown as text so nothing in it can be hidden. `approve` shows the task first and asks you to type yes, and works only in an interactive terminal; approving runs nothing yet. Declines, approvals and tasks left unanswered until they expire are reported to the room. ID may be any unique start of a task id.
- A teammate's daemon now receives tasks sent to them, including ones sent while they were offline, and checks each one against the room lead's registered signing key before keeping it. Tasks that fail the check are kept as rejected, with the reason, and none of their content is trusted. Listing, approving and running tasks follow in the next releases.
- `crewbo task create --to LOGIN [--path PATH]... [--for DURATION] (TEXT | --file FILE)` lets a room lead send a signed task to a teammate's agent. Approving and running tasks follow in the next releases.
- In a repository that is in a room, `crewbo claim add` and `crewbo claim release` go through the sync server: a teammate's claim blocks your agents' edits on their machine and yours, and you are told who holds a file. Claims made offline are kept locally, shared on reconnect, and dropped (with a note in `crewbo status`) if someone else took the file meanwhile.
- The daemon connects to the sync server for repositories in a room (after `crewbo login` and `crewbo room create` or `join`), catches up after a server restart or time offline, and keeps working locally when it cannot connect. `crewbo status` shows the sync state.
- `crewbo room create | invite | join | leave | status`, run inside a git repository, put that repository in a room on the sync server: the creator is the lead, invites are codes valid 24 h for up to 9 people by default, and a room holds at most 10 members.
- `crewbo login` also creates this device's signing key (kept in the system keychain, or in a file readable only by you when no keychain answers within 3 s) and registers its public key with the sync server.
- `crewbo login --server URL` signs in with GitHub (device flow: open github.com/login/device and enter the code shown) and saves a 7-day Crewbo session for that sync server. `crewbo serve` now issues these sessions, requires one on every daemon connection, and keeps its data in `server.db` (`--data DIR`).
- `crewbo serve [--addr HOST:PORT] [--tls-cert FILE --tls-key FILE] [--insecure-lan]` runs the sync server skeleton: `/healthz` and the daemon WebSocket at `/v1/ws` (Hello and Welcome only; rooms and claims follow). Plain HTTP is allowed only on loopback unless `--insecure-lan` is given.
- `crewbo version` prints the version and commit; `crewbo help` prints usage.
- `crewbo daemon` runs the per-user daemon in the foreground and stops cleanly on Ctrl+C (and SIGTERM on Linux and macOS).
- `crewbo status` reports whether the daemon is running, with its version, process id, uptime, active claims and agent sessions.
- `crewbo hook claude-code|codex <event>` enforces claims inside Claude Code and Codex: an edit to a file claimed by someone else is denied with the holder's name.
- `crewbo hooks install` and `crewbo hooks uninstall` add or remove Crewbo's hooks in Claude Code (`~/.claude/settings.json`, exec form) and Codex (`~/.codex/hooks.json`), keeping other hooks and writing a backup.
- `crewbo mcp` serves read-only MCP tools, `crewbo_claims` and `crewbo_who_holds`, so agents can see claims before planning edits.
- After a shell command, Crewbo checks whether it changed a file someone else claimed (for example through a script) and tells the agent; `crewbo status` counts these violations.
- `crewbo claim add [--for 30m] [--task ID] <path or glob>...`, `crewbo claim list` and `crewbo claim release <id>...` claim files in the current repository from a terminal.
