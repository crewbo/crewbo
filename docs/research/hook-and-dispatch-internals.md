# Native binaries, not scripts, should own every hook

The adapter layer for v1 should be **one Go binary invoked directly by both agents' hook systems**, not shell scripts. Claude Code and Codex now share almost the same hook contract (JSON on stdin, `hookSpecificOutput.permissionDecision:"deny"` to block, exit 2 as a hard block), so a single `sangam hook <event>` subcommand can gate edits to claimed files in both, provided it also parses shell commands, because `sed -i`, redirects and heredocs bypass the file-edit tool matchers in both agents. Windows is the reason to drop scripts: Claude Code's exec form spawns a real `.exe` with no shell, while shell-form hooks run through Git Bash, which strips backslashes from paths. Dispatched tasks should still launch through each agent's own headless CLI (`claude -p`, `codex exec`) under the teammate's login, but the plan gains two native push paths: Claude Code's per-session messaging socket (on by default since v2.1.224) and, for Codex threads the daemon itself owns, the App Server's `turn/steer`. Three prior assumptions change: WIP refs every 30 s would breach GitHub's recommended **6 pushes per minute per repository** at three active users, Protobuf should stop generating MCP schemas, and hooks become a compiled binary. What stays unproven is mostly wire-level: the Claude socket frame format is undocumented, Codex hook trust pinning and Windows quoting need live tests, and several Git and keyring version floors rest on recollection rather than release notes.

## Both agents block edits with one JSON shape, but differ in five places

Claude Code reads hooks from a `"hooks"` key in `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed policy or a plugin's `hooks/hooks.json`. All levels merge and changes hot-reload into running sessions ([Hooks reference](https://code.claude.com/docs/en/hooks); [Settings](https://code.claude.com/docs/en/settings)). Codex reads `hooks.json` or a `[hooks]` table in `config.toml` at `~/.codex/` and `<repo>/.codex/`, runs all matching hooks from all layers, and loads project hooks only when the project is trusted ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). The nesting is identical (event, then matcher group, then handler list), which lets one generator emit both. Install user-level hooks, not project-level, so the adapter works in every repo without committing files teammates did not ask for.

The recommended Claude Code registration uses exec form, which requires `args` and spawns the binary with no shell:

```json
{"hooks":{
  "SessionStart":[{"hooks":[{"type":"command","command":"C:/Users/r/AppData/Local/sangam/bin/sangam.exe","args":["hook","cc","session-start"]}]}],
  "UserPromptSubmit":[{"hooks":[{"type":"command","command":"<abs>/sangam","args":["hook","cc","prompt"]}]}],
  "PreToolUse":[
    {"matcher":"Edit|Write|MultiEdit|NotebookEdit","hooks":[{"type":"command","command":"<abs>/sangam","args":["hook","cc","pre-edit"]}]},
    {"matcher":"Bash|PowerShell","hooks":[{"type":"command","command":"<abs>/sangam","args":["hook","cc","pre-shell"]}]}],
  "PostToolUse":[{"matcher":"Edit|Write|MultiEdit|NotebookEdit|Bash|PowerShell","hooks":[{"type":"command","command":"<abs>/sangam","args":["hook","cc","post-tool"]}]}],
  "Stop":[{"hooks":[{"type":"command","command":"<abs>/sangam","args":["hook","cc","stop"]}]}]}}
```

A Claude `PreToolUse` input carries `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input` and `tool_use_id`; Edit and Write put the target in `tool_input.file_path`, NotebookEdit in `notebook_path`, and Bash and PowerShell in `tool_input.command` ([Agent SDK types](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk); [Tools reference](https://code.claude.com/docs/en/tools-reference)). The deny response is `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"src/auth.ts is claimed by Priya (task #12)"}}`. Four contract details matter for correctness. A deny **blocks even under `bypassPermissions` and `--dangerously-skip-permissions`**, because PreToolUse fires before any permission-mode check. Exit 0 with no output means "no decision", not approval. A schema-valid JSON object on stdout decides regardless of exit code. And a missing or non-executable hook (exit 127) is a silent non-blocking error, so a mistyped path disables the gate without warning ([Hooks guide](https://code.claude.com/docs/en/hooks-guide); [Hooks reference](https://code.claude.com/docs/en/hooks)). Timeouts fail open: a timed-out PreToolUse hook does not block unless the handler sets `onFailure:"block"`, available since **v2.1.295**. Defaults are 600 s for command hooks, **30 s for `UserPromptSubmit`**, and a shared **1.5 s budget for `SessionEnd`**, while `additionalContext` is capped at 10,000 characters ([Hooks reference](https://code.claude.com/docs/en/hooks)).

Codex accepts the same deny JSON and the same exit-2 block, but diverges in five ways an adapter must encode ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). First, **every non-managed hook is hash-pinned and skipped until trusted** through `/hooks` in the TUI; `--dangerously-bypass-hook-trust` skips this for one invocation, and only managed hooks in `requirements.toml` are trusted by policy. Second, file edits arrive as `tool_name:"apply_patch"` (also matchable as `Edit` or `Write`) with `tool_input:{"command":"<raw patch>"}`, so paths must be parsed from `*** Add File:`, `*** Update File:`, `*** Delete File:` and `*** Move to:` headers ([openai/codex pre_tool_use.rs](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/events/pre_tool_use.rs); [apply_patch.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/apply_patch.rs)). Third, the PreToolUse output schema sets `additionalProperties:false`, and `"ask"`, `continue`, `stopReason` and `suppressOutput` are unsupported: emitting any of them **fails the hook run and lets the tool proceed**. Fourth, exit-2 reasons are read from stderr. Fifth, model-visible hook output is capped near 2,500 tokens unless `additionalContextLimit` overrides it. Codex input also adds `model` and `turn_id`.

The trust gate argues for a design choice the notes support only by inference: keep the hook entry byte-for-byte stable (an absolute path to `sangam` plus fixed arguments) and put all logic in the binary, so a teammate trusts the hook once and upgrades never re-trigger review. Whether Codex's hash covers only the config entry or also the target file is unverified and is a Phase 0 test. If it covers the binary, the fallback is a managed hook via `requirements.toml` on machines where the teammate administers their own policy, or `--dangerously-bypass-hook-trust` for daemon-dispatched `codex exec` runs only, where the daemon vets its own hook file.

### Shell edits need a parser at PreToolUse and a diff at PostToolUse

Claude Code's own auto-mode classifier lists "`python -c`, `sed -i`, `cat >`, heredocs" as ways to circumvent Edit and Write deny rules, and OpenAI calls Codex hooks "a useful guardrail, not a complete enforcement boundary" ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). Claude's `if` filter cannot close the hole because it is explicitly "best-effort" ([Hooks reference](https://code.claude.com/docs/en/hooks)). The recommended `pre-shell` handler parses `tool_input.command` into an AST with a Go POSIX shell parser (mvdan.cc/sh is the obvious candidate) and extracts write targets from redirections (`>`, `>>`, heredoc into a file), in-place editors (`sed -i`, `perl -i`), `tee`, `cp`, `mv`, `rm`, `truncate`, `git checkout -- <path>`, `git apply` and `git restore`. PowerShell commands need a smaller token-level check for `Set-Content`, `Add-Content`, `Out-File`, `Remove-Item`, `Move-Item` and `>`. Resolve each target against `cwd`, normalize, and deny if it hits a claim held by someone else. Where the target cannot be resolved statically (variables, `$(...)`, scripts that write files), deny only if a claimed path string appears literally in the command alongside a write verb; otherwise allow.

The fallback is detection after the fact. A `post-tool` handler for `Bash|PowerShell` compares the content hashes of currently claimed paths in the worktree (or runs `git status --porcelain -z` scoped to them) before and after the call. On a violation it reports to the coordinator and returns `additionalContext` telling the agent which claim it crossed. In Codex, PostToolUse `decision:"block"` replaces the tool result with that feedback but **does not undo the action** ([Codex hooks](https://learn.chatgpt.com/docs/hooks)), so v1 should alert and record, not auto-revert. For dispatched Codex runs, the `--json` stream's `file_change` items give an authoritative list of edited paths ([openai/codex exec_events.rs](https://github.com/openai/codex/blob/main/codex-rs/exec/src/exec_events.rs)).

Hook latency and failure policy deserve an explicit choice. The hook binary should talk to the local daemon over a Unix socket or named pipe with its own deadline of a few hundred milliseconds, and on an unreachable daemon it should **allow and inject a warning** rather than block. Blocking every edit because the daemon crashed punishes the teammate for the tool's bug. Do not set Claude's `onFailure:"block"` in v1 for the same reason; reserve it for a future "strict" team policy.

## Windows runs Claude hooks through Git Bash and Codex hooks through cmd.exe

Claude Code's shell-form hooks run through `sh -c` on macOS and Linux, Git Bash on Windows, or PowerShell when Git Bash is absent, which since v2.1.120 to 126 is a supported configuration ([Hooks reference](https://code.claude.com/docs/en/hooks); [What's new W18](https://code.claude.com/docs/en/whats-new/2026-w18.md)). Shell form is unsafe for paths: Git Bash strips backslashes, so `C:\Users\x\probe.ps1` becomes `C:Usersxprobe.ps1` and exits 127, an issue closed "not planned" ([claudeissues #54640](https://claudeissues.com/issue/54640-bug-hook-command-on-windows-backslashes-in-absolute-paths-are-shell-mangled-befo)). Non-interactive Git Bash can also source profiles, and a stray `echo` corrupts the JSON on stdout ([Hooks guide](https://code.claude.com/docs/en/hooks-guide)). Exec form avoids all of this, but on Windows `command` must resolve to a real executable; npm `.cmd` and `.bat` shims cannot be spawned without a shell ([Hooks reference](https://code.claude.com/docs/en/hooks)). A Go `.exe` satisfies that by construction. Use forward slashes in the configured path anyway, and normalize incoming `file_path` values (backslashes, drive-letter case) before comparing against claims. The fallback for Claude versions that predate `args` is shell form with a forward-slash path and no profile-dependent behavior; no minimum version for exec form is documented, so the installer should check `claude --version`.

Codex has no exec form. Its hook runner wraps the command line in quotes and runs it via `%COMSPEC%` (falling back to `cmd.exe`) with `/C` on Windows, using `CREATE_NO_WINDOW`; on Unix it runs `$SHELL -lc`, falling back to `/bin/sh` ([openai/codex command_runner.rs](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/engine/command_runner.rs)). The recommended config sets both `command` and the Windows-only `commandWindows` (TOML `command_windows`) to the absolute binary path plus fixed arguments ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). Two hazards follow, and both are inferences that Phase 0 must test. The `-lc` login shell on Unix sources the teammate's profile, which can pollute stdout just as Git Bash profiles do on Claude, and Omarchy users who set `$SHELL` to zsh or fish get that shell's login semantics. On Windows, cmd.exe quoting breaks on paths containing spaces or `&`, and `%LOCALAPPDATA%` contains the Windows username. Installing the binary to a space-free path, or emitting the 8.3 short path, is the defensive fallback. Codex hooks are spawned by the harness rather than the sandboxed exec path, so a hook's IPC call to the daemon should not be sandboxed, though the docs do not state this explicitly.

Git hooks follow the same rule. Git for Windows runs hook files through its bundled `sh`, so the safe default is a two-line `#!/bin/sh` shim that `exec`s `sangam.exe hook git <event> "$@"`. On Git versions that support config-based hooks (`hook.<name>.command` plus `hook.<name>.event`), register the binary directly instead, which avoids clobbering `core.hooksPath` setups owned by husky or lefthook ([git-hook docs](https://git-scm.com/docs/git-hook)). The exact Git version where config-based hooks became usable for standard events is unverified, so feature-detect with `git hook list`.

## Dispatched tasks keep the teammate's login, and two push paths now exist

### Claude Code: `claude -p` without `--bare`, explicit permission mode, inbox accepting

The daemon should spawn Claude in the task worktree as the working directory, since `-p` has no `--cwd` flag, with: `claude -p "<prompt>" --output-format stream-json --verbose --permission-mode acceptEdits --session-id <uuid> --name sangam/<task> --settings '{"crossSessionInbound":"accept"}'`. Without `--bare`, a `-p` session loads the same user, project and local settings, hooks, CLAUDE.md, MCP servers and permission rules as an interactive one and authenticates through the teammate's subscription login, which is exactly "the teammate's own permissions and auth" ([Headless](https://code.claude.com/docs/en/headless)). `--bare` is wrong here on three counts: it skips hooks and MCP (so the adapter's own gates vanish), never reads OAuth or the keychain, and binds no messaging socket; the docs also warn it will become the `-p` default in a future release, so the daemon should pin the behavior it wants explicitly ([Headless](https://code.claude.com/docs/en/headless); [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)).

Always pass `--permission-mode`. Its `-p` default varies by provider and version (`default` normally, `auto` since v2.1.285 for sessions that skip feature flags), and in `-p` anything that would prompt is denied, so `default` mode leaves a dispatched task unable to edit ([Permission modes](https://code.claude.com/docs/en/permission-modes)). `acceptEdits` matches what most teammates expect; `dontAsk` is the strict alternative that only runs pre-approved tools. Because PreToolUse hooks fire in every mode, claim enforcement survives either choice. Scrub `ANTHROPIC_API_KEY` from the child environment unless the teammate opted into API billing, because in `-p` "the key is always used when present" and silently overrides the subscription ([Authentication](https://code.claude.com/docs/en/authentication)). Preflight with `claude auth status`, which exits 1 when logged out. Read `session_id` from the first `system/init` event and the outcome from the final `result` event; SIGTERM yields exit 143 and still runs `SessionEnd` hooks ([Headless](https://code.claude.com/docs/en/headless)). The fallback for teammates who want to watch or take over a task is `claude --bg "<prompt>"`, which starts a supervised background session that `claude attach` can join, though it cannot combine with `-p` ([CLI reference](https://code.claude.com/docs/en/cli-reference)).

### Claude Code push: capture the socket in `SessionStart`, post with the token

Every non-bare session since v2.1.224 on macOS, Linux and WSL2, and v2.1.234 on native Windows, binds a per-session inbox (Unix socket or named pipe) and exports `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` to hooks and Bash before any hook runs ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging); [Env vars](https://code.claude.com/docs/en/env-vars)). The recommended path: the `session-start` hook sends `session_id`, socket path and token to the daemon, which keeps the token in memory only. To push, the daemon connects, writes `{"type":"auth","token":"..."}` as the first line (required on Windows, where the connection is otherwise closed), then the message line, and closes. Connections that do not complete a line within 30 s are dropped, so open the socket only when the message is ready. The receiver reads the message between tool calls or, if idle, starts a new turn, and it fires `UserPromptSubmit` in the receiver, so the prompt hook sees pushed messages too ([Hooks reference](https://code.claude.com/docs/en/hooks)).

The message frame itself is **undocumented**. The v2.1.296 binary's debug hint shows `{"type":"user","message":{"role":"user","content":"hello"}}`, and a hidden session registry at `~/.claude/sessions/<pid>.json` lists `messagingSocketPath`, `sessionId` and `status`; both were observed in a local binary, not in docs. Delivery is also conditional: with no `crossSessionInbound` setting, a session running in `bypassPermissions` holds messages it cannot verify as coming from its own child processes, and `-p` sessions drop held messages after five minutes ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). Dispatched sessions avoid this via `crossSessionInbound:"accept"`; interactive sessions depend on whether the token makes an external daemon count as an "own child". So treat the socket as a **wake-up and urgent-conflict channel**, and keep the documented channel, `additionalContext` from `UserPromptSubmit` and `PostToolUse`, as primary. The fallback is hooks only, which still deliver team state on the next prompt or tool call.

### Codex: `codex exec` for v1, App Server ownership as the upgrade

The daemon should run `codex exec --json -C <worktree> --sandbox workspace-write -o <last-message-file> "<prompt>"`. Exec defaults to `approval_policy=never` in headless mode, reads `~/.codex/config.toml` (so the teammate's hooks, MCP servers and model settings apply), and authenticates from the existing ChatGPT login under `CODEX_HOME`; `CODEX_API_KEY` overrides it for CI ([openai/codex exec/src/lib.rs](https://github.com/openai/codex/blob/main/codex-rs/exec/src/lib.rs); [shared_options.rs](https://github.com/openai/codex/blob/main/codex-rs/utils/cli/src/shared_options.rs)). `--full-auto` is gone and the `untrusted` approval mode was retired, so older scripts that use them will error ([Daniel Vaughan](https://codex.danielvaughan.com/2026/08/31/codex-cli-sandbox-permission-hardening-full-auto-removed-untrusted-retired-fail-closed/)). The JSONL stream yields `thread.started` with `thread_id`, then `turn.*` and `item.*` events; follow-ups go through `codex exec resume <thread_id> "<prompt>"`.

Exec offers no mid-task push. The native path is `codex app-server`, a JSON-RPC 2.0 server over stdio (with the `"jsonrpc"` field omitted on the wire) that powers the VS Code extension ([App Server](https://learn.chatgpt.com/docs/app-server)). After `initialize` and `initialized`, the daemon can `thread/start` with `cwd`, `approvalPolicy` and `sandbox`, start work with `turn/start`, append input to an active turn with `turn/steer` (which **requires `expectedTurnId`** and fails if another turn is active), or add silent context with `thread/inject_items` ([openai/codex turn.rs](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/turn.rs)). This only works on threads the daemon's own app-server process holds: Codex thread-store locks are process-local, and agent-bridge, the one public implementation, resumes threads and queues new turns rather than attaching to a live TUI session ([agent-bridge codex-channel](https://github.com/EthanSK/agent-bridge/blob/main/codex-channel/README.md)). The recommendation is to ship v1 on `codex exec`, matching the prior plan, and spike an App Server driver in Phase 0. If it holds up, switch dispatched Codex tasks to daemon-owned App Server threads, generating client types from `codex app-server generate-json-schema` for the exact installed version. A teammate's own interactive Codex TUI stays hooks-only.

## Hand-written Go structs should define MCP schemas, Protobuf only the wire

The prior plan made Protobuf the single source of truth and generated MCP schemas from it. That should change. The official MCP Go SDK (v1.8.0, 14 Sep 2026) infers input and output JSON Schemas from Go structs through `google/jsonschema-go`, takes field descriptions from `jsonschema:"..."` tags, and validates both arguments and output at runtime ([go-sdk releases](https://github.com/modelcontextprotocol/go-sdk/releases); [go-sdk server docs](https://github.com/modelcontextprotocol/go-sdk/blob/main/docs/server.md)). The generator route is weak: bufbuild's `protoc-gen-jsonschema` is self-described alpha, and chrusty's was archived in June 2024 ([bufbuild/protoschema-plugins](https://github.com/bufbuild/protoschema-plugins); [chrusty/protoc-gen-jsonschema](https://github.com/chrusty/protoc-gen-jsonschema)). Passing `protoc-gen-go` structs straight to `mcp.AddTool` is a trap, because they carry internal fields and protojson semantics (camelCase names, int64 as strings) that reflection-based inference will not describe.

The two layers also want different shapes. MCP schemas face a model and should be flat, terse and enum-light; Protobuf messages face the wire and carry oneofs and well-known types. With about six tools, define dedicated `In`/`Out` structs per tool, tighten constraints by mutating `jsonschema.For[T]()` output (min, max, enums) before assigning `Tool.InputSchema`, and keep Protobuf plus protovalidate for daemon-to-server traffic. Replace codegen with two tests: a round-trip table test from each MCP struct to its proto request, and golden-file snapshots of each tool's generated schema to catch drift. Keep the server's `instructions` under **2,048 characters**, Claude Code's default truncation point, and put the claim-check rule first; set `_meta["anthropic/alwaysLoad"]` on the one or two tools Claude must always see ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). Codex surfaces the same `instructions` as the tool namespace description ([openai/codex rmcp_client.rs](https://github.com/openai/codex/blob/main/codex-rs/codex-mcp/src/rmcp_client.rs)). Register with `claude mcp add --scope user --transport stdio sangam -- <abs>/sangam mcp` and `codex mcp add sangam -- <abs>/sangam mcp`. The fallback, if the tool count grows large or tools must mirror proto messages one to one, is to revisit protoschema-plugins once it leaves alpha.

## Store the Ed25519 seed in the keychain, with a fast-failing file fallback

Sign with stdlib `crypto/ed25519` and persist only the 32-byte seed, base64-encoded, through `zalando/go-keyring`. It is pure Go with no cgo, uses macOS's `/usr/bin/security`, Linux's Secret Service over D-Bus, and Windows Credential Manager under target `service:username` ([zalando/go-keyring](https://github.com/zalando/go-keyring)). `99designs/keyring` offers more backends, including an encrypted file, but pkg.go.dev shows its last release as v1.2.2 from December 2022 ([pkg.go.dev 99designs/keyring](https://pkg.go.dev/github.com/99designs/keyring)). Keychain-less Linux is a real, common failure: "org.freedesktop.secrets was not provided by any .service files" recurs on NixOS and Arch, and the same gap breaks other CLIs on headless machines ([NixOS Discourse](https://discourse.nixos.org/t/the-name-org-freedesktop-secrets-was-not-provided-by-any-service-files/36406); [Obsidian forum](https://forum.obsidian.md/t/ob-sync-setup-fails-on-headless-linux-keychain-unavailable/111679)). Omarchy's Hyprland desktop falls into the at-risk group unless a Secret Service provider is running, which the notes did not verify.

Copy gogcli's detection pattern: on Linux, skip the keyring when `DBUS_SESSION_BUS_ADDRESS` is empty, and wrap the first keyring call in a timeout of a few seconds because D-Bus activation can hang ([instagit on gogcli](https://instagit.com/steipete/gogcli/what-keyring-backends-does-gog-support-and-how-does-it-handle-credential-storage-across-platforms)). On failure, fall back to `$XDG_CONFIG_HOME/sangam/device.key`, written atomically at mode 0600 in a 0700 directory, which matches the accepted norm of a passphrase-less `~/.ssh/id_ed25519`. A password-encrypted file sounds safer but hurts an unattended daemon, since the password ends up in an environment variable anyway. Expose `SANGAM_KEY_BACKEND=file|keyring` and the active backend in `sangam doctor`. On Windows the file fallback should be DPAPI-protected, because 0600 bits do not map to ACLs; that is an inference, not a sourced fact. Use per-device keys registered server-side with `added_at` and `revoked_at`, include a key ID in each signed envelope, sign a domain-separated deterministic encoding, and persist the verification result at ingest so later revocation blocks new events without invalidating history, the model GitHub uses for commit signature records ([GitHub signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)).

## Custom refs work on GitHub, but a 30-second push cadence does not scale

GitHub accepts pushes to arbitrary namespaces such as `refs/sangam/wip/<user>/<task>` and does not display them, the same mechanism git-bug uses for `refs/bugs/<id>` ([git-bug data model](https://github.com/git-bug/git-bug/blob/trunk/doc/design/data-model.md)). Default fetch and push cover only heads and tags, so the daemon must pass explicit refspecs on every call rather than editing the teammate's `remote.origin.fetch`: push with `git push --atomic --force-with-lease=<ref>:<oid> origin <local>:refs/sangam/wip/<user>/<task>`, and fetch with `git fetch origin '+refs/sangam/*:refs/sangam-remote/origin/*'` so remote WIP never overwrites local refs ([viblo: git as a database](https://viblo.asia/p/git-as-a-database-what-git-bug-teaches-us-about-storing-data-in-refs-8X4EjqKAJN2)). Avoid `refs/heads/*`, which would trigger Actions, rulesets and PR UI, and `refs/pull/*`, which GitHub reserves.

The prior plan's cadence is the problem. GitHub recommends at most **6 pushes per minute per repository**, enforces a 2 GB push size, and suggests no more than 5,000 branches per repo ([GitHub repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)). One push per user every 30 s is 2 per minute per user, so three concurrently active teammates hit the ceiling. The recommendation moves liveness to the coordination server and pushes Git refs only on change, debounced to a checkpoint interval of a few minutes or on task state changes, batching all of a user's refs into one atomic push and deleting refs when tasks complete. The fallback, for repos near the limit, is a per-repo global push budget enforced by the server that hands out push slots. The 6-per-minute figure is a recommendation; no hard enforcement threshold or error is documented, and whether push rulesets or secret-scanning push protection inspect custom namespaces is also undocumented ([GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)).

### Shell out to system Git, with a 2.38 floor and Windows guards

go-git v6 supports only fast-forward merges, no rebase, partial linked worktrees and no signing, so it cannot do conflict prediction ([go-git COMPATIBILITY.md](https://github.com/go-git/go-git/blob/main/COMPATIBILITY.md)). Shell out with `os/exec` to a `git` resolved once via `exec.LookPath`, require **Git 2.38+** for `merge-tree --write-tree`, and treat its exit codes as authoritative (0 clean, 1 conflicts) rather than inferring cleanliness from empty output; in `--stdin` batch mode the per-merge status is inverted and the process exits 0 ([git-merge-tree](https://git-scm.com/docs/git-merge-tree)). Current Git for Windows is 2.56.0.windows.2 (5 Oct 2026), which also fixes `GIT_CONFIG_GLOBAL=NUL`, broken in 2.56.0 ([Git for Windows releases](https://github.com/git-for-windows/git/releases/latest)). On Windows, pass `-c core.longpaths=true -c core.quotepath=false` on every call, because long-path support is off by default and other tools still hit 260 characters ([Git for Windows long paths](https://gitforwindows.org/git-cannot-create-a-file-or-directory-with-a-long-path.html)). Keep worktrees short (for example `%LOCALAPPDATA%\sangam\wt\<shorthash>`), run `git worktree prune` at startup, retry `worktree remove` with backoff, set `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C`, spawn with `CREATE_NO_WINDOW`, and kill process trees through Job Objects. When the daemon runs Git from inside a Git hook, clear `GIT_DIR` and the other local environment variables the githooks docs warn about ([githooks](https://git-scm.com/docs/githooks)).

## What changes, and what Phase 0 must prove

| Area | Recommended | Fallback | Change vs prior plan |
|---|---|---|---|
| Hooks | One Go binary; Claude exec form, Codex `command` plus `commandWindows`; stable entries | Shell form with forward slashes; Codex managed hooks | Scripts replaced by a native binary |
| Shell edits | AST parse at PreToolUse, hash diff at PostToolUse | Literal path plus write-verb deny; alert only | New requirement |
| Claude dispatch | `claude -p`, no `--bare`, explicit `--permission-mode`, inbox `accept` | `claude --bg` for attachable tasks | Unchanged CLI, flags pinned |
| Claude push | Messaging socket, token from `SessionStart` | Hook `additionalContext` only | New native path |
| Codex dispatch | `codex exec --json --sandbox workspace-write` | Same, plus `resume` | Unchanged |
| Codex push | Daemon-owned App Server threads, `turn/steer` | Hooks only | New, gated on spike |
| MCP schemas | Go structs plus golden tests | protoschema-plugins after alpha | Protobuf no longer generates MCP schemas |
| Keys | go-keyring, D-Bus probe with timeout | 0600 file (DPAPI on Windows) | Detailed |
| WIP refs | Checkpoint pushes, liveness via server | Server-issued push budget | 30 s pushes dropped |
| ACP | Not used | Not used | Unchanged |

Phase 0 should run eight spikes, each with a binary pass condition. First, post to an **interactive** Claude session's socket from a non-child daemon on Linux, macOS and native Windows, both with and without the token, and confirm delivery rather than a hold in `default` and `bypassPermissions` modes; this also pins down the undocumented frame and the Windows pipe naming. Second, change only the `sangam` binary behind a trusted Codex hook and check whether Codex demands re-trust. Third, install the binary under a path with a space and run a Codex hook through cmd.exe, and run a Unix hook under bash, zsh and fish login shells with a noisy profile. Fourth, confirm Claude exec-form hooks on a Windows machine without Git Bash and record the minimum Claude version that supports `args`. Fifth, drive a 20-command corpus of shell edits (`sed -i`, heredocs, `tee`, PowerShell `Set-Content`, `python -c`) through both agents and measure what the parser blocks and what the diff catches. Sixth, run `turn/steer` and `thread/inject_items` against a daemon-owned Codex thread and record the `codex exec` exit code on `turn.failed`. Seventh, check whether `jsonschema.For` marks non-`omitempty` fields as required and which draft it emits. Eighth, push custom refs at 10 per minute to a scratch GitHub repo to observe whether any throttling appears, and confirm the Git versions for `merge-tree --merge-base` and config-based hooks against release notes, along with keyring size limits and Omarchy's default Secret Service status.

## Conclusion

The biggest shift is that enforcement now lives in compiled code the team controls, not in agent configuration. Because Claude Code and Codex converged on one hook vocabulary, the adapter is less two integrations than one policy engine with two thin input decoders, and every new agent with a PreToolUse-style gate becomes a decoder, not a project. That raises the stakes on the shell parser: it is the single component whose accuracy decides whether claims are a lock or a suggestion, and its corpus test results are worth publishing alongside the conflict-prevention metric from the earlier strategy work.

The second shift is that push is real but asymmetric. Claude offers it into sessions the teammate started; Codex offers it only into sessions the daemon owns. That asymmetry suggests a product rule rather than a workaround: interactive sessions get awareness and enforcement through hooks, while daemon-dispatched sessions get full steering. Designing the UI around that split, rather than promising uniform live control, keeps v1 honest about what each vendor actually exposes.
